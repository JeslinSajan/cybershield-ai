# CyberShield AI — Use Cases

Version 1.0 | Companion to SRS.md

Each use case references functional requirements from
`functional-requirements.md` where applicable.

---

## UC-1: Register an Agent

- **Actor:** Administrator
- **Related FRs:** FR-4.1, FR-4.2
- **Preconditions:** Administrator is logged in; the target host has
  the CyberShield Agent software installed.
- **Main Flow:**
  1. Administrator generates an enrollment token in the dashboard.
  2. Administrator configures the Agent with the token and Backend URL.
  3. Agent sends a registration request using the token.
  4. Backend validates the token and issues an Agent credential.
  5. Agent stores the credential and begins sending heartbeats.
- **Postconditions:** The Agent appears in the Agent list as
  registered and, once a heartbeat is received, as ONLINE.

## UC-2: Monitor Agent Health

- **Actor:** Administrator, Security Analyst
- **Related FRs:** FR-4.3, FR-4.4
- **Preconditions:** Agent is registered.
- **Main Flow:**
  1. Agent sends periodic heartbeat with status and health data.
  2. Backend updates the Agent's last-seen timestamp and status.
  3. Dashboard reflects ONLINE/OFFLINE state.
- **Postconditions:** Users can see, at a glance, which Agents are
  currently reachable.

## UC-3: Discover Devices on an Authorized Network

- **Actor:** Administrator, Security Analyst
- **Related FRs:** FR-5.1, FR-5.2, FR-5.3, FR-5.4
- **Preconditions:** An Agent is online; user has permission to run
  scans.
- **Main Flow:**
  1. User initiates a discovery scan from the dashboard, acknowledging
     the authorized-use notice.
  2. Backend sends the scan task to the selected Agent.
  3. Agent runs Nmap-based discovery on the local network.
  4. Agent reports discovered devices to the Backend.
  5. Backend stores devices; dashboard updates the Device List.
- **Postconditions:** Newly discovered devices are visible with IP,
  hostname, open ports, and status.

## UC-4: Run a Vulnerability Scan

- **Actor:** Administrator, Security Analyst
- **Related FRs:** FR-6.1, FR-6.2, FR-6.3, FR-6.4
- **Preconditions:** Device already discovered.
- **Main Flow:**
  1. User selects a device and initiates a vulnerability scan.
  2. Agent performs port/service/version detection.
  3. Backend matches results against local/cached CVE data.
  4. Backend calculates severity and risk contribution.
  5. Vulnerabilities appear in the Vulnerability List with
     recommendations.
- **Postconditions:** Device's risk score is updated to reflect newly
  found vulnerabilities.

## UC-5: Investigate an Alert

- **Actor:** Administrator, Security Analyst
- **Related FRs:** FR-9.1–FR-9.4, FR-12.1, FR-12.2, FR-12.3, FR-13.1
- **Preconditions:** An alert has been generated by the threat
  detection engine.
- **Main Flow:**
  1. User opens the Alert List and selects an alert.
  2. User views the alert's description, related device/agent, and
     risk score.
  3. User requests an explanation from the Local Security Explanation
     Engine.
  4. User transitions the alert's status (e.g. Open → Investigating).
  5. User adds notes/resolution and marks it Resolved or False
     Positive.
- **Postconditions:** Alert status and timeline reflect the
  investigation; audit log records the status changes.

## UC-6: Generate a Security Report

- **Actor:** Administrator, Security Analyst
- **Related FRs:** FR-14.1, FR-14.2
- **Preconditions:** The system has at least some devices,
  vulnerabilities, and/or alerts recorded.
- **Main Flow:**
  1. User selects a time period and report type from the Reports view.
  2. Backend aggregates devices, vulnerabilities, alerts, and risk
    distribution for that period.
  3. Backend generates a PDF/CSV file.
  4. User downloads the report.
- **Postconditions:** A report file exists reflecting the selected
  period's actual data (never fabricated placeholder content).

## UC-7: Manage Users and Roles

- **Actor:** Administrator
- **Related FRs:** FR-2.1, FR-2.2, FR-2.3
- **Preconditions:** Administrator is logged in.
- **Main Flow:**
  1. Administrator opens User Management.
  2. Administrator creates a new user and assigns a role
     (Administrator / Security Analyst / Viewer).
  3. System enforces that the last remaining Administrator cannot be
    demoted or deleted.
- **Postconditions:** New user can log in with the assigned role's
  permissions.

## UC-8: View Read-Only Dashboard (Viewer Role)

- **Actor:** Viewer
- **Related FRs:** FR-3.2, FR-17.1, FR-17.2, FR-17.3
- **Preconditions:** Viewer account exists and is logged in.
- **Main Flow:**
  1. Viewer opens the dashboard and browses summary cards, charts, and
     recent activity.
  2. Viewer attempts a write action (e.g. running a scan) and receives
    an HTTP 403 / disabled UI control.
- **Postconditions:** Viewer has full visibility with zero ability to
  alter system state.
